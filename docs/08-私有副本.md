# 08 · 私有副本

分析记录、真实持仓成本、生成的报告 —— 这些**不该进公开仓**，但你自己要留、
要跟着版本走、要能换机器带走。做法是：**公开仓 clone 一份当私有副本**，
公开仓挂成 `upstream`，你自己的私有仓当 `origin`。

```
GitHub
  TbusOS/astock-lab        public   ← 工具 + skills + 文档
  <你的私有仓>              private  ← 上面全部 + 你的数据

本机
  ~/astock-lab-private/    clone 自公开仓，origin=你的私有仓，upstream=公开仓
```

---

## 一次性搭建

```bash
git clone https://github.com/TbusOS/astock-lab.git ~/astock-lab-private
cd ~/astock-lab-private

git remote rename origin upstream                 # 公开仓 → upstream
gh repo create <你的私有仓> --private --source=. --remote=origin
# 或手动:git remote add origin git@github.com:<你>/<私有仓>.git

bash scripts/setup_private.sh                     # 建 private/ 并让 data/ 可 track
bash install.sh                                   # 建 venv、装依赖、链 skills
git push -u origin main
```

`setup_private.sh` 会拦住两种配错：`origin` 和 `upstream` 指向同一个仓，
或者 `origin` 还指着公开仓 —— 这两种情况下 push 会把你的持仓数据推上公开仓。

## ★ data/ 为什么能被 track：一个 git 的硬限制

公开仓的 `.gitignore` 写的是 **`data/*`**，不是 `data/`。这不是随手写的：

> git 不允许「父目录被排除之后再反选其中的文件」。

写成 `data/`（整个目录被排除）→ 你在私有副本里**永远没法**把 `data/journal.jsonl`
加进版本控制，`git add -f` 也只是一次性的，下次照样忽略。

写成 `data/*`（只排除内容，不排除目录本身）→ 子文件可以被反选回来。
于是私有副本只需要一个 `data/.gitignore`：

```gitignore
!*
perf_cache/     # 缓存能重拉，占地方，不进仓
```

**这个文件只存在于私有副本**，公开仓根本没有它 —— 所以每次同步零冲突。

实测验证过两种写法：`data/` 那种，`data/journal.jsonl` 被 track 的数量是 **0**；
`data/*` 那种是 **1**。

**同样的规则适用于 `private/`**，公开仓写的也是 `private/*`。
这条是踩出来的：第一版把 `private/` 写成带斜杠，私有副本建好 `private/` 塞进
6.4 MB 个人文件后 `git add -A` —— **一个都没进去**，而且不报错。
`git add -A` 对被忽略的路径是静默跳过的，你只有去数暂存了几个文件才会发现。

### 还有一个：`.venv` 不要带斜杠

`.venv/` 只匹配目录。如果你的 `.venv` 是**指向别处的软链**（复用已有环境），
它是个文件不是目录，`.venv/` 匹配不到，那个软链会被提交上去。
公开仓写的是不带斜杠的 `.venv`。

## 什么进哪个仓

| 内容 | 公开仓 | 私有副本 |
|---|---|---|
| 工具代码、skills、文档 | ✅ 真身 | ✅ 从上游同步 |
| `private/portfolio/` 真实持仓与成本 | ❌ 被 gitignore | ✅ |
| `private/reports/` 生成的报告 | ❌ | ✅ |
| `private/sessions/` 会话记录 | ❌ | ✅ |
| `data/journal.jsonl` 决策记录 | ❌ | ✅ |
| `data/principles.jsonl` 蒸馏出的原则 | ❌ | ✅ |
| `data/perf_cache/` 基准率缓存 | ❌ | ❌（能重拉，别进仓） |
| `repos/` 第三方开源仓 | ❌ | ❌（各自有 .git） |

## 日常：拉公开仓的更新

```bash
bash scripts/sync_from_upstream.sh --check    # 只看有什么更新
bash scripts/sync_from_upstream.sh            # 看完问你要不要合
bash scripts/sync_from_upstream.sh --yes      # 直接合
```

它会先拦住脏工作区（merge 撞上未提交改动是最难收拾的情况），
然后列出上游领先的提交和会动到的文件，`private/` 与 `data/` 被显式排除在 diff 之外。

**用 merge 不用 rebase**：你的私有副本有公开仓永远不会有的提交。
rebase 会把这些提交重写在上游之上 —— 每次同步都改写你自己的历史，
一旦冲突就在半路停住，状态很难解释。merge 只加一个合并提交，你的历史原样保留。

合完建议跑一遍 `bash scripts/check_gates.sh` 再 `git push origin main`。

## 反向：你在私有副本里改进了工具，想推回公开仓

改动如果是**通用的**（修了 bug、加了工具、补了数据源），值得推回去：

```bash
cd ~/astock-lab-private
git format-patch upstream/main --stdout -- skills/ tools/ docs/ scripts/ > /tmp/x.patch

cd ~/astock-lab                       # 公开仓的工作副本
git checkout -b feature/xxx
git am /tmp/x.patch
bash scripts/check_gates.sh           # ★ 零个人信息闸必须过
git push origin feature/xxx
```

**`format-patch` 的路径限定不是可选的** —— 不加 `-- skills/ tools/ ...` 会把
`private/` 和 `data/` 的提交也打进补丁。`check_gates.sh` 是最后一道兜底，
但别指望它替你把关：它查的是个人痕迹的**已知模式**，不是全知全能。
